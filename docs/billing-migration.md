# 課金 baseline の切替手順

新しい課金処理は、請求レコードの作成時に対象ユーザーの `baseline_member_ids` を同時保存する。月次処理の再実行とユーザー登録イベントは共通のメンバーイベント台帳を利用するため、snapshot に含まれるユーザーの後着イベントやイベント再送を二重計上しない。

既存請求レコードに baseline がない場合、新登録の加算・月次再照合は明示的なエラーとなる。このデータ移行を終えるまで、新しい課金処理でユーザー登録を再開してはならない。サーバーのデプロイ成功だけでは切替完了としない。

## 維持する業務仕様

- 月内にユーザーが無効化されても、既存の請求人数・金額を減額しない。新たなユーザーの加算は法人・請求月・ユーザーIDで重複排除する。
- 価格・税率は変えず、計算を Decimal の整数円・切捨てに統一する。
- 現行LambdaのUTC基準の25日/26日境界を明示して維持する。JST基準への変更は正式な業務要件確認後の別移行とする。
- 過去のCognitoページ処理不具合による人数・請求への実影響は未確認。現在の人数との差分だけで過去金額を自動訂正しない。

## 計画の作成

このCLIはローカルJSONを読み、条件付き更新の計画だけを生成する。AWS接続・SDK client生成・更新実行・自動適用オプションはない。

```sh
python scripts/plan_billing_baseline.py \
  --invoice /tmp/invoice.json \
  --members /tmp/members.json \
  --table StageBills \
  --output /tmp/billing-baseline-plan.json
```

入力の最小例:

```json
{"user_id":"example-corp","context":"history_202610","history":{"users_count":2,"price":1100,"raw_price":1000,"tax":1.10,"status":"pending","invoice_number":1,"invoice_date":"2026/10/31"}}
```

```json
[{"user_id":"example-user-a"},{"user_id":"example-user-b"}]
```

実際のinvoiceには保存されている `history` 全体を渡す。条件式はその完全一致を確認するので、途中で請求内容が変わった場合は更新を拒否する。入力は通常のJSON型で、DynamoDB AttributeValue形式ではない。

計画には入力ファイルSHA-256、現状の請求内容、一意人数と重複数、請求人数との差分、追加するbaseline、型付きDynamoDB UpdateItem要求を含む。変更対象は `baseline_member_ids` だけで、金額・状態・請求番号は変更しない。

baselineが既にある、請求人数が現在の一意人数より小さい、不正な入力である場合は計画作成を失敗させる。請求人数が大きい場合は、月内の無効化など正当な理由と過去の不具合の両方が考えられるため、差分を明示して人が確認する。計画の生成成功は請求額の正当性を証明しない。

## リリースゲート

1. 対象法人・請求期間を確定し、現行データのbackup/復元方法を確認する。
2. ユーザー登録・有効化/無効化・課金書込みを停止し、処理中の登録と課金イベントを完了または解決する。snapshot前後に未完了の登録が残る状態でbaselineを作らない。
3. 同一時点のinvoiceと対象メンバーを読み取り、計画を作成する。入力・計画は個人IDを含むため、通常の運用データとして管理する。
4. 差分と既存請求の妥当性を確認する。訂正が必要なら、この移行とは別の変更計画で扱う。
5. レビュー済みの `conditional_update_request` を承認された運用経路で適用する。条件失敗なら再取得・再計画し、条件を外して強制適用しない。このリポジトリの計画CLIは適用を行わない。
6. baselineと金額不変を照合し、隔離環境で登録イベント再送・月次再実行・同時登録を検証する。
7. 全対象法人の現請求期間が移行済みであることを確認し、新しい課金コードを有効化して登録を再開する。

切戻しはbaselineを残して新方式を扱える互換版までとする。新方式のユーザー加算後に旧方式へ戻すと、メンバーイベント台帳を無視して二重請求し得る。旧コードへ戻す必要がある場合は再び登録・課金書込みを停止し、データと未処理イベントを照合して別途計画する。
